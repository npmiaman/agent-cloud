# Agent Cloud can own the storage boundary

Every problem on the list already has a credible partial solution. RFC 8693 token exchange and Keycard handle credential narrowing. Microsoft Entra Agent ID handles authority decay. Claude Code auto mode handles risk-scored approval. CaMeL and FIDES handle information-flow control. LiteLLM handles session budgets. lakeFS, Dolt and Cloudflare Artifacts handle branching, and Fast.io and LucidLink handle leases. Crypto-shredding libraries handle erasure. Zep/Graphiti handles bi-temporal memory. Temporal, DBOS and Restate handle durable execution, OpenTelemetry handles tracing, and MCP plus A2A handle interop. The weakness they share is architectural: **each one keeps its state in its own store, apart from the files agents read and write**. So provenance labels, budgets, decision records, validity windows and delegation chains all disappear at exactly the point where one agent's output becomes another agent's input. Agent Cloud already owns that point. It has immutable per-file versions with stable ids, an audit log with request ids, per-agent credentials, approvals with diffs, idempotency keys and an MCP server. Its opening is to attach a small, permanent, signed **provenance record to every version and every credential**, and to build coordination, safety, retention and portability features on top of it. The first job is not a feature, though. **The MCP 2026-07-28 spec retired the `initialize` handshake**, and Agent Cloud currently delivers agent identity and its "since your last session" briefing in the `initialize` response. That has to move before anything else ships. The rest of this report covers what exists in each of the nine problem areas, where the real gaps are, and a build order that puts the fixes that compound earliest at the top.

A note on ground truth. The research notes were written against a brief that partly differed from Agent Cloud's actual state, and the corrections below apply throughout. Metadata lives in **SQLite (WAL, multi-process), not Postgres**. There is **no S3 backend**. Blob dedup is **already scoped per organisation**, never across orgs. Agents can re-share a subset of their access but **cannot mint sub-credentials yet**. Researcher proposals that assume Postgres (DBOS-style rows, `SELECT … FOR UPDATE SKIP LOCKED`) or S3 (lifecycle tiers, Parquet archives) are adapted here rather than repeated. One researcher's brief also listed per-workspace storage quotas and per-credential rate limits. Those are not in the confirmed feature list, so treat them as unverified.

## Delegated authority is standardised for one hop and decays only inside Entra

The base primitive has settled. Vendors build on RFC 8693 token exchange with `act` chains. Keycard's May 2026 multi-agent product runs a policy check on every exchange and narrows permissions at each hop, so "no agent ever holds more" ([Help Net Security](https://www.helpnetsecurity.com/2026/05/15/keycard-for-multi-agent-apps/)). Above that primitive, the agent-specific standards are thin. The on-behalf-of draft covers only the single hop from user to agent and has not been adopted by the OAuth working group ([WorkOS](https://workos.com/blog/oauth-on-behalf-of-ai-agents)). Transaction Tokens for Agents carry an `actor` and a `principal` through a call chain, but define neither budgets nor a multi-hop chain record ([IETF draft -04](https://www.ietf.org/archive/id/draft-oauth-transaction-tokens-for-agents-04.html)). The only agent OAuth extension in real production is **ID-JAG / Cross App Access**. Its short-lived, audience-bound assertion (Okta's example expires in 300 s) lets an enterprise IdP apply policy before a cross-app grant ([Okta](https://developer.okta.com/blog/2025/06/23/enterprise-ai)). MCP adopted it as the stable Enterprise-Managed Authorization extension ([MCP blog](https://blog.modelcontextprotocol.io/posts/enterprise-managed-auth/)). Biscuit tokens support offline attenuation, where any holder can add restrictions and verification needs only a public key ([docs.rs](https://docs.rs/crate/biscuit-auth/0.8.0)). The identity researcher found no shipping agent product built on them. The OpenID Foundation's whitepaper sums up the state of the field: existing SSO breaks down for autonomous agents, and "scalable oversight" is missing ([OpenID Foundation](https://openid.net/new-whitepaper-tackles-ai-agent-identity-challenges/)).

MCP adds no delegation of its own. The 2025-11-25 authorization spec is a clean OAuth 2.1 resource-server profile. It makes RFC 9728 Protected Resource Metadata mandatory, requires RFC 8707 audience binding and PKCE S256, and **forbids token passthrough**: a server calling upstream must act as a separate OAuth client ([MCP authorization spec](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)). Its default, though, pushes the wrong way. If the 401 challenge names no scope, clients request all of `scopes_supported`. Combined with long-lived refresh tokens, that produces broad, durable grants, the opposite of decay.

On decay itself, **Microsoft Entra Agent ID is the reference design, and it is the only shipping one**. Every agent identity needs a human sponsor, and sponsorship moves to the sponsor's manager when the sponsor leaves. Access packages expire unless the sponsor extends them. A default inactivity policy notifies people and then disables idle agents. Disabling a blueprint blocks every identity created from it ([MS Learn governance overview](https://learn.microsoft.com/en-us/entra/id-governance/agent-id-governance-overview); [owners/sponsors](https://learn.microsoft.com/en-us/entra/agent-id/agent-owners-sponsors-managers)). All of it requires Microsoft 365 E7 or Agent 365 licensing and an Entra tenant. AWS IAM Access Analyzer flags unused roles and keys but knows nothing about agents ([AWS docs](https://docs.aws.amazon.com/IAM/latest/UserGuide/access-analyzer-findings.html)). Kill-switch practice exists only as practitioner guidance. A kill must revoke credentials, stop running jobs and sit outside the agent's own authority, and it should be drilled by measuring how long tokens keep working afterwards ([nhimg.org](https://nhimg.org/articles/ai-kill-switches-must-sit-outside-agent-authority-boundaries)). Keeping secrets out of model context is now a common product claim. Arcade injects tokens at tool-call time ([Arcade docs](https://docs.arcade.dev/en/home/build-tools/create-a-tool-with-auth)). Keycard's sidecar swaps placeholders for real secrets ([keycard.ai](https://keycard.ai/)). 1Password gates browser autofill behind a human ([1Password](https://1password.com/blog/closing-the-credential-risk-gap-for-browser-use-ai-agents)). Every one of these claims is vendor-sourced, and none protects authority, only the secret value.

**The gap** has four parts, and no self-hosted product covers any of them. The first is agent-minted sub-credentials that carry budgets, task binding and expiry, not just scope. The second is a queryable delegation tree with subtree revocation. The third is decay that cascades down that tree. The fourth is a kill switch with a measured revocation window. Agent Cloud is closer than it looks. Its rule that an agent can re-share only a subset of its access is already attenuation semantics. Its 15-minute access tokens with immediate revocation already beat MCP's "short-lived SHOULD" and bound the post-kill window. The missing piece is the mint endpoint. It should accept an RFC 8693-shaped request with the parent token as `subject_token` and constraint fields (`max_calls`, `max_bytes_written`, `not_after`, `task_id`, `allowed_tools`). Each mint is stored as an edge in a delegation table, so "revoke everything descending from agent X" becomes one query. Budgets are enforced server-side, which Agent Cloud can do because it is the data plane, and that avoids Biscuit's offline-verification complexity. Entra's sponsor model translates directly: a required human owner of record and a `reauth_every` cadence. When a re-auth is missed or the owner is deactivated through OIDC/SCIM, the agent auto-pauses and the pause cascades to every descendant. Agent Cloud should also publish its revocation latency as a measured number, because no vendor publishes one.

## Approval, injection and budget controls all stop at the tool call, not the data change

### Human approval scales only when a classifier shrinks the queue

Approval tooling comes in two shapes. One is a binary per-tool gate: OpenAI Agents SDK `needs_approval` returning a resumable `RunState` ([OpenAI Agents Python](https://openai.github.io/openai-agents-python/human_in_the_loop)), or HumanLayer's decorator that routes approvals to Slack or email ([PyPI](https://pypi.org/project/humanlayer/)). The other is a deterministic policy engine at a gateway. **Amazon Bedrock AgentCore Policy** went GA on 3 March 2026. It enforces Cedar policies on every agent-to-tool call, is default-deny once a policy is attached, and generates its schema from the gateway's MCP tool manifest ([AWS](https://aws.amazon.com/about-aws/whats-new/2026/03/policy-amazon-bedrock-agentcore-generally-available); [docs](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy.html)). The one risk-based auto-approver with published numbers is **Claude Code auto mode**. Anthropic found users accept **93% of manual permission prompts**, which is the rubber-stamp failure in a single figure. Auto mode puts a two-stage transcript classifier in front of every action. The full pipeline runs at **0.4% false-positive rate, with 17% false negatives on real overeager actions and 5.7% on synthetic exfiltration**. It escalates to a human after 3 consecutive or 20 total denials ([Anthropic Engineering](https://anthropic.com/engineering/claude-code-auto-mode)). Research on reviewer fatigue makes the same point formally: the safety-optimal escalation rate is below "escalate everything" ([arXiv 2606.08919](https://arxiv.org/pdf/2606.08919)).

What is missing is review of the **data change itself**. AgentCore decides whether an agent may call a tool on a resource, but it never sees the content of the write. Claude Code's classifier explicitly skips in-project file edits. The governance researcher found no product that risk-scores a diff by blast radius (searching was limited, about four queries). Agent Cloud's approval policies (none/overwrite/all), diffs that include CSV column changes, and stale-proposal checks are the right substrate. Its `all` mode, though, is exactly the setting the 93% figure predicts will turn into rubber-stamping. The upgrade is a risk score per proposal built from deterministic features Agent Cloud already holds: rows and columns touched, schema changes, deletes, how many other agents read the file, how recently other agents read it, and whether the writer's inputs were tainted (next subsection). Proposals then route to `auto` / `review` / `block`. Agent Cloud should also batch similar proposals from one task into one aggregate diff, add circuit breakers modelled on Claude Code's 3/20 denial rule, and track approval rates per reviewer so it can detect fatigue. On the protocol side, the 2026-07-28 MCP spec's Multi Round-Trip Requests (`resultType: "input_required"`) fit a pending approval naturally. That lets any MCP client see an Agent Cloud approval as an ordinary input request ([MCP blog](https://blog.modelcontextprotocol.io/posts/2026-07-28/)).

### Provenance labels die at the storage boundary, and that is where injection spreads

The strongest prompt-injection defences are deterministic information-flow control. **CaMeL** (Google DeepMind) tags values with capabilities and provenance and runs plans in a tracking interpreter. It solves **77% of AgentDojo tasks with provable security, against 84% undefended** ([arXiv 2503.18813](https://arxiv.org/abs/2503.18813)). **FIDES** (Microsoft Research) tracks confidentiality and integrity labels, blocked all prompt-injection attacks in AgentDojo with policy checks on, and ships experimentally in Microsoft Agent Framework ([Microsoft Research](https://www.microsoft.com/en-us/research/publication/securing-ai-agents-with-information-flow-control/)). Both work **inside a single run**. MemLineage points out that FIDES labels are erased at the run boundary ([arXiv 2605.14421](https://arxiv.org/pdf/2605.14421)). Persistent stores are therefore the propagation channel. MINJA plants malicious memory records through ordinary queries alone, with **98.2% injection success** reported in an earlier paper version ([arXiv 2503.03704](https://arxiv.org/abs/2503.03704)). A 2026 joint evaluation bypassed 12 published prompt-injection defences ([arXiv 2604.16548](https://arxiv.org/html/2604.16548)). OWASP's December 2025 Agentic Top 10 lists "Memory and Context Poisoning" as ASI06 ([OWASP](https://genai.owasp.org/2025/12/09/owasp-top-10-for-agentic-applications-the-benchmark-for-agentic-security-in-the-age-of-autonomous-ai/)). Several 2026 preprints propose cross-session provenance (the Agentic Reference Monitor, memory provenance laundering). None is a product, and the researcher found no storage system that carries taint labels through to readers. Mem0, Zep and Letta were not specifically searched, so read this as "not found", not "confirmed absent".

This is **the clearest unoccupied gap in the whole survey, and it sits on Agent Cloud's boundary**. Here is the failure. Agent A reads a poisoned web page and writes `summary.md`. Agent B reads `summary.md` as trusted workspace data. The design that closes it has four steps. First, record per version the writer principal, the source class (human, agent, external:web, upload), and the input file versions the writing task read, with read sets taken from the audit log keyed by task id. Second, let each version inherit the lowest trust of its inputs. Third, return `trust`/`origin` fields in every read response, with optional datamarking for low-trust content. Fourth, sign the record, reusing the existing webhook signing, so the labels have the integrity MemLineage says current approaches lack. Policy hooks follow naturally, such as "writes derived from external content require approval". So does a lineage query that lists every downstream version and reader of a flagged version for quarantine or revert. The researcher flags the honest cost: taint by read set over-taints, so anything that touches the web becomes low-trust. A human "endorse" action is therefore needed, and the same declassification problem exists in CaMeL and FIDES.

### Spend caps are mature for LLM tokens and absent for everything else

Gateways have solved LLM spend. **LiteLLM** virtual keys carry `max_budget` and `budget_duration` ([LiteLLM](https://docs.litellm.ai/docs/proxy/users)). Its agent iteration budgets add `max_iterations` and `max_budget_per_session` keyed by a required trace id, and return HTTP 429 with `"type": "budget_exceeded"` ([LiteLLM iteration budgets](https://docs.litellm.ai/docs/a2a_iteration_budgets)). OpenRouter enforces org, workspace and per-key caps on every request ([OpenRouter](https://openrouter.ai/docs/guides/features/workspaces/workspace-budgets)). Portkey keeps budget limits on its Enterprise tier ([Portkey](https://portkey.ai/docs/product/ai-gateway/virtual-keys/budget-limits.md)). Every one of these budgets **LLM tokens only**. None caps bytes written, files touched, proposals filed, egress, webhook fan-out or approval requests per agent or per task, and none detects behavioural runaway in a data store. Agent Cloud should copy LiteLLM's mechanics (a required task id, counters per (agent, task), a machine-readable 429, a TTL) and apply them to its own resources, enforced inline. It can also see runaway signals that no LLM gateway can: the same file overwritten N times in one task, content hashes oscillating, rejected or stale proposals churning, read amplification, and writes continuing after denials. A kill switch should do three things in one call: revoke the credential subtree, freeze pending proposals, and emit a signed webhook. "Revert everything task X wrote" then becomes a version-history operation, because every write is already versioned.

## Shared-storage products each ship one of branching, leases or erasure

### Multi-agent coordination: branch, lease, and commit atomically

Agent storage in 2025-2026 has split into four groups. **Turso AgentFS** (beta, open source) is copy-on-write: a SQLite delta layer over a read-only base, with every file operation and tool call audited ([Turso docs](https://docs.turso.tech/agentfs/guides/overlay); [auditing](https://docs.turso.tech/agentfs/guides/auditing)). POSIX volumes over object storage form the second group. Modal Volumes are explicitly **last-write-wins with no distributed locking** ([Modal](https://www.modal.com/docs/guide/volumes)). Daytona volumes attach to one sandbox at a time ([Daytona](https://www.daytona.io/docs/en/persistence)). Archil fronts S3/R2/GCS for E2B and Mastra ([Archil](https://docs.archil.com/details/architecture)). The third group is MCP-fronted shared stores with locks. **Fast.io** documents leases with a secret `lock_token`, `expires_at`, heartbeat renewal, HTTP 409 on contention and expiry-based takeover ([Fast.io](https://fast.io/resources/implement-file-locks-fastio-api/)). **LucidLink's** proprietary MCP server (public beta, June 2026) offers global file locking ([Blocks & Files](https://www.blocksandfiles.com/file/2026/06/29/lucidlink-giving-ai-agents-file-access-with-mcp/5263643)). The fourth group is git-shaped repos. **Cloudflare Artifacts** (beta, April 2026) maps each repo to a Durable Object and charges $0.15 per 1,000 operations ([Cloudflare blog](https://blog.cloudflare.com/artifacts-git-for-agents-beta/); [product page](https://www.cloudflare.com/product/artifacts/)). In data infrastructure, lakeFS builds transactions out of branches: branch, write, merge, and roll back by not merging ([lakeFS](https://docs.lakefs.io/reference/python/transactions/)). DoltHub rebranded in June 2026 as "the Database for Agents" ([DoltHub](https://dolthub.com/blog/2026-06-03-branch-bench-database-benchmarking-for-agentic-workflows)).

Research is consistent on which primitive matters. CRDTs guarantee convergence but not correctness. CodeCRDT saw **100% convergence and still 5-10% semantic conflicts** across 600 trials ([arXiv 2510.18893](https://www.arxiv.org/pdf/2510.18893)). AgentRoom found that removing the explicit claim/status tools while keeping the CRDT **loses most of the coordination gain** ([arXiv 2608.23740](https://arxiv.org/pdf/2608.23740)). So the right design for Agent Cloud is **leases plus compare-and-swap plus branch/merge, not CRDTs**. A lease call (`acquire(file_id | path_prefix, ttl) → {lease_id, fencing_token, expires_at}`, plus heartbeat, release and admin takeover) closes the gap with Fast.io and LucidLink. The fencing token, checked on every CAS write, makes leases safe against holders that were paused and woke up late. That is standard distributed-systems practice and not drawn from a cited source. Atomic multi-file commit is a small step from the current design. Write immutable content-addressed blobs first, then CAS-swap one branch head that points to a manifest of `{file_id → version_id}`. That is the same architecture lakeFS, Dolt and Artifacts use. Agent Cloud's **stable file ids across moves make three-way merge rename-safe**, where git has to infer renames heuristically. In SQLite the head swap is one `UPDATE … WHERE head = :expected` inside a `BEGIN IMMEDIATE` transaction, which WAL mode serialises cleanly.

### Retention and erasure: regulators want proof, not editable backups

The EDPB's coordinated-enforcement report on the right to erasure (adopted 10 February 2026; 32 authorities, 764 controllers) sets the bar. It accepts that modifying backups "might not always be advisable". It still expects controllers to "keep track of erasure requests and comply with them on restored systems", to "verify that erasure has been carried out and be able to demonstrate such erasure", and not to exclude backups by default. **Half of responding authorities raised backup erasure as a problem** ([EDPB CEF report §4.2.6](https://www.edpb.europa.eu/system/files/2026-02/edpb_cef-report_2025_right-to-erasure_en.pdf)). The report never mentions crypto-shredding. Crypto-shredding is still the standard engineering answer for immutable stores: per-subject keys, destroyed to erase, as implemented in event-sourcing libraries ([cqrs-es-crypto](https://docs.rs/cqrs-es-crypto)). Its known hole is unencrypted snapshots and derived state, and whether it legally counts as erasure is debated: encrypted personal data is arguably still personal data ([Verraes](https://verraes.net/2019/05/eventsourcing-patterns-throw-away-the-key/)). WORM storage conflicts with erasure directly. S3 Object Lock compliance mode cannot be bypassed even by the root user, short of deleting the AWS account ([AWS](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html)). S3 lifecycle rules (keep N noncurrent versions, transition, expire) are the cost model customers already know ([AWS](https://docs.aws.amazon.com/AmazonS3/latest/API/API_NoncurrentVersionExpiration.html)).

Agent Cloud already solves one concern the storage researcher raised. Dedup is per organisation, so erasing one org's data can never delete another org's blob, and a content hash cannot confirm content across orgs. Two concerns remain. Within an org, identical content from two data subjects still dedups to one blob, so per-subject erasure requires **dedup scoped to a subject key domain** wherever a file is tagged with a subject. Second, the AES-256-GCM chunk encryption has to sit under a key hierarchy (data key, wrapped by an org key-encryption key, optionally by a per-subject one) for shredding to be possible at all. That hierarchy was not checked against the code. The full erasure path then has five steps: destroy the subject key in every key store, including the replica and key backups; append to an erasure ledger; hard-delete the blobs at the next retention purge; issue a verifiable receipt; and **replay the ledger before serving from any restored backup**. The last step is the explicit EDPB expectation that most controllers miss. Agent Cloud's online, hard-linked, verified backups and its blob replica with integrity scrub need to carry the ledger, not just the data. Retention should grow from a single per-workspace purge window into a policy object: `keep_versions`, `cold_after_days`, `expire_after_days`, plus a scoped, governance-style legal hold that blocks purge but not shredding for subjects outside its scope. Without an S3 backend, "cold" means a compressed local tier for now. The researcher also inferred that whole-blob dedup means every edit to a large file stores a full new copy. Hugging Face's Xet replaced Git LFS with roughly 64 KB content-defined chunks for exactly this reason ([HF Xet](https://huggingface.co/docs/hub/xet/index)). Whether Agent Cloud's encryption chunks are also dedup units is unverified and worth checking before any retention-cost claims are made.

## Memory and execution engines keep state away from the agent's files

### Memory: full context still wins on accuracy, files win on portability

Memory systems have settled into three designs ([Claude memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool); [Mem0 paper](https://arxiv.org/html/2504.19413v1); [Zep paper](https://arxiv.org/html/2501.13956v1)). The first is **file memory the agent edits itself**. Anthropic's `memory_20250818` tool is client-side: Claude issues view/create/str_replace/insert/delete/rename, and the developer maps `/memories` onto real storage. It leaves expiry, size caps, traversal checks and versioning to the implementer. The second is **LLM-extracted fact stores**. Mem0 picks ADD/UPDATE/DELETE/NOOP and resolves contradictions by physically deleting the old fact. The third is **bi-temporal graphs**. Zep/Graphiti stores `t_valid`/`t_invalid` alongside system timestamps, invalidates contradicted facts instead of deleting them, and traces every fact back to a raw source episode. Letta's sleep-time agents add a curation pattern. The conversational agent cannot edit its core memory, and a background agent rewrites it asynchronously ([Letta](https://www.letta.com/blog/sleep-time-compute)). The benchmark that matters cuts against the marketing. On LoCoMo, **full context scores 72.9%, above Mem0 (66.9%), Zep (66.0%) and OpenAI (52.9%)**. Memory buys about 1.8k tokens per query against about 26k, and 1.44 s p95 latency against 17.1 s ([Mem0 paper, vendor-authored](https://arxiv.org/html/2504.19413v1)). The value of memory is cost, persistence and auditability, not accuracy, and Agent Cloud should not claim otherwise.

Context efficiency follows the same logic. Anthropic's guidance treats context as finite because of "context rot". It recommends compaction, clearing tool results, note-taking outside the window, and just-in-time retrieval by reference: paths, queries, line ranges ([Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). Sleep-time compute cuts test-time compute about 5x at equal accuracy when queries are predictable ([arXiv 2504.13171](https://arxiv.org/abs/2504.13171)). Agent Cloud's own measurement backs this approach. With a real Claude Haiku agent, targeted edits cut a one-line change in a 300-line file **from 32.7 s to 8.0 s and from 5,808 to 706 output tokens** (internal measurement). The next step is precomputed per-version derived views built at write time (file summaries, directory digests, changed-since digests), served in the briefing and expanded by line range on demand. Embeddings, if added, have to be keyed by `(file_id, version, embedding_model)`, because they are not portable across embedding models.

The cheapest wedge in the whole report is here. **Agent Cloud's MCP tool set already maps almost one-to-one onto Anthropic's memory-tool commands**: line-range reads to `view`, cloud_edit to `str_replace`, cloud_append and inserts, create, delete, rename. A drop-in remote backend for `memory_20250818` gives every Claude model that supports the tool versioned, audited, shared memory, which Anthropic's reference handler lacks. Because files are versioned, "invalidate, don't delete" comes for free: a superseded fact survives in the previous version.

### Model migration and world staleness have no owner

Vendors treat model migration as rewriting prompts and running evals. OpenAI ships a prompt optimizer and per-model upgrade guides, and it warns against treating GPT-5.5 as a drop-in replacement ([OpenAI](https://developers.openai.com/api/docs/guides/upgrading-to-gpt-5p5)). Memory portability exists only inside ecosystems: Letta's .af across Letta servers ([Letta](https://docs.letta.com/guides/agents/agent-file)), and OpenMemory MCP across clients but on Mem0's own schema ([Mem0](https://mem0.ai/blog/introducing-openmemory-mcp)). Agent identity across a model swap has three parts: instructions, accumulated memory, and evals that prove behaviour survived. Nobody versions the three together. Agent Cloud can, with a pinned agent profile (charter + memory snapshot + model id) per version, an eval set stored in the workspace, and an old-vs-new diff report before a switch.

For world staleness, Graphiti is the only memory system with first-class validity intervals. Link-rot tooling is mature but sits outside agents. Internet Archive's SPN2 API supports `if_not_archived_within` ([SPN2 docs](https://docs.google.com/document/d/1Nsv52MvSjbLb2PCpHlat0gkzw0EvtSgpKHu4mk0MnrA/mobilebasic)). ArchiveBox self-hosts WARC/HTML/PDF snapshots ([PyPI](https://pypi.org/project/archivebox/0.9.34rc63/)). Perma.cc's evidence on the scale of the problem: **over 70% of law-journal URLs from 1999-2011 no longer point to the cited content** ([Perma blog](https://archive.blogs.harvard.edu/perma/2019/02/14/so-how-bad-a-problem-is-link-rot)). No surveyed product attaches snapshots or validity windows to agent research outputs, or schedules re-verification. Agent Cloud can close that loop with three pieces. First, a `capture(url)` tool that stores the snapshot as a versioned file. Second, a facts sidecar (`claim, source_url, retrieved_at, content_hash, snapshot_ref, valid_until, recheck_at`) that is invalidated, never deleted. Third, a maintenance-worker job that re-fetches sources on `recheck_at` and reports "3 facts expired, 1 source 404s, 2 writes contradict file X v12" in the next session briefing.

### Durable execution is crowded; data-triggered wake-ups and decision provenance are not

Durable execution for agents is a solved category for control flow. **Temporal's OpenAI Agents SDK integration** went GA for Python on 23 March 2026. It turns each model call into an Activity, but its durability explicitly does not extend to MCP servers ([Temporal docs](https://docs.temporal.io/develop/python/integrations/openai-agents-sdk)). For weeks-to-years workflows, Temporal recommends pinned versions plus Upgrade-on-Continue-as-New ([Temporal](https://temporal.io/blog/ga-worker-versioning-public-preview-upgrade-on-continue-as-new)). **DBOS** checkpoints each step into Postgres rows and offers `patch()` for in-flight upgrades ([DBOS](https://docs.dbos.dev/architecture)). **Restate** guarantees a single writer per key ([Restate](https://docs.restate.dev/ai/patterns/sessions)). Inngest sleeps for up to a year within the plan's run limit ([Inngest](https://www.inngest.com/docs/durable-execution/primitives/step-sleep)). Cloudflare Workflows sleep up to 365 days without counting against concurrency ([Cloudflare](https://developers.cloudflare.com/workflows/reference/limits)). Trigger.dev waitpoint tokens can be completed by an unauthenticated POST to a callback URL ([Trigger.dev](https://trigger.dev/docs/wait-for-token)). AgentCore Runtime is a session runtime, not durable execution: 8-hour default lifetime, 14 days maximum with instances ([AWS](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-lifecycle-settings.html)). Every one of these models the agent as a workflow run kept in its own store, and **none wakes an agent when a file changes**. That trigger is built by hand from webhooks plus `waitForEvent`.

Agent Cloud should not build a replay engine. It should build a thin task table **in SQLite**. The researcher's Postgres `FOR UPDATE SKIP LOCKED` design does not carry over. The SQLite equivalent is an atomic `UPDATE tasks SET lease_owner=?, lease_expires_at=? WHERE id=(SELECT … due and unleased LIMIT 1) RETURNING *` under WAL's single writer, with the maintenance worker reclaiming expired leases. Waits accept `{file_path, version > n}`, a webhook event, a waitpoint token, or a cron. File writes mark matching waiters due. Each wake-up is a fresh short run seeded by the "since your last session" briefing, which sidesteps replay versioning the way Continue-as-New does. A per-(agent, lane) singleton lease prevents two runs of one agent from fighting. SQLite's single writer caps how fast tasks can be claimed. That ceiling is fine for self-hosted single-node deployments, and it is one more reason a Postgres backend eventually earns its place.

Long-horizon observability fails for a different reason: **traces expire while files persist**. Hosted defaults are short: Datadog LLM Observability 15 days ([Datadog](https://docs.datadoghq.com/llm_observability/data_governance/)), LangSmith base 14 days ([LangSmith](https://docs.langchain.com/langsmith/usage-and-billing)). Self-hosted Langfuse OSS ([Langfuse](https://github.com/orgs/langfuse/discussions/7460)) and Arize Phoenix ([Phoenix](https://arize.com/docs/phoenix/settings/data-retention)) keep data indefinitely. The EU AI Act requires high-risk systems to allow automatic logging "over the lifetime of the system" ([Art. 12](https://artificialintelligenceact.eu/article/12/)), with logs kept at least six months ([Art. 19](https://artificialintelligenceact.eu/article/19/)). That floor exceeds every hosted default above. OTel's GenAI agent conventions carry `gen_ai.agent.id`/`version`, `gen_ai.request.model` and `_ref` pointers, but all are at Development status and **nothing links a span to "file F, version 17"** ([OTel agent spans](https://raw.githubusercontent.com/open-telemetry/semantic-conventions-genai/main/docs/gen-ai/gen-ai-agent-spans.md)). MCP's OTel conventions propagate `traceparent` in `params._meta` ([OTel MCP](https://opentelemetry.io/docs/specs/semconv/gen-ai/mcp/)), so Agent Cloud can stamp the caller's trace id onto every version and audit row without client changes. Add a tiny permanent decision row per version (trace id, agent version, requested and returned model, charter hash, input file@version refs, short rationale, request id), and "why did the agent change F six months ago" becomes one join that survives trace expiry. Audit and decision partitions can be hash-chained per month and moved to compressed local files. The default retention should be at least six months.

## Protocols move messages, not agents, and MCP just broke Agent Cloud's handshake

MCP now has neutral governance. It went to the Linux Foundation's Agentic AI Foundation on 9 December 2025, with AWS, Google, Microsoft and OpenAI among the platinum members ([LF](https://linuxfoundation.org/press/linux-foundation-announces-the-formation-of-the-agentic-ai-foundation)). The current spec, **2026-07-28, turns MCP into a stateless request/response protocol**. It retires the `initialize`/`initialized` handshake and the `Mcp-Session-Id` header. Every request now carries its protocol version, client identity and capabilities in `_meta`, with an optional new `server/discover` RPC. Multi Round-Trip Requests replace server-initiated elicitation and sampling. Roots, Sampling, Logging and HTTP+SSE are deprecated with at least 12 months of support. Streamable HTTP requests must carry `Mcp-Method` and `Mcp-Name` headers. List and read responses gain `ttlMs`/`cacheScope`. Tasks become the `io.modelcontextprotocol/tasks` extension with `tasks/get`, `tasks/update` and `subscriptions/listen` ([MCP blog](https://blog.modelcontextprotocol.io/posts/2026-07-28/); [SEP-2663](https://modelcontextprotocol.io/seps/2663-tasks-extension.md)).

**This is a required change for Agent Cloud.** Today its agent identity and "since your last session" briefing arrive in the `initialize` response, and a 2026-07-28 client will never send `initialize`. Identity has to come from per-request `_meta` client info plus the bearer token. The briefing has to move to something a stateless client can fetch: a `cloud_briefing` tool, a briefing MCP resource with a short `ttlMs`, and optionally `server/discover` metadata. The "since your last session" cursor also has to become server-side state keyed by the agent credential, because a session id no longer exists. While Agent Cloud is in this code, it should publish RFC 9728 metadata and validate RFC 8707 audiences, emit the routing headers, advertise `ttlMs` on versioned file resources (immutable versions can be cached indefinitely), implement the Tasks extension on top of the task table, and map approvals onto `input_required`. The interop researcher did not verify whether `resources/subscribe` survives the stateless core. Live file sync depends on it, so that needs checking against the spec text.

Above MCP, **A2A reached v1.0 in March 2026** ([Google](https://opensource.googleblog.com/2026/04/a-year-of-open-collaboration-celebrating-the-anniversary-of-a2a.html)). It joined AAIF in August 2026 ([AAIF](https://aaif.io/blog/a2a-joins-aaif)) and ships in Azure AI Foundry, Copilot Studio and Bedrock AgentCore ([LF](https://www.linuxfoundation.org/press/a2a-protocol-surpasses-150-organizations-lands-in-major-cloud-platforms-and-sees-enterprise-production-use-in-first-year)). v1.0 adds JWS-signed Agent Cards, a `tenant` field so one endpoint can serve many agents, `ListTasks`, artifacts and push-notification configs, and it **says nothing about how tasks or artifacts are stored** ([A2A whats-new-v1](https://raw.githubusercontent.com/a2aproject/A2A/main/docs/whats-new-v1.md)). Agent definition formats cover fragments. Letta .af serialises memory blocks, messages, tools and config, but excludes archival memory, files, MCP configs and multi-agent setups, and nulls secrets ([agent-file README](https://raw.githubusercontent.com/letta-ai/agent-file/main/README.md)). Oracle Open Agent Spec is definition only ([arXiv 2510.04173](https://arxiv.org/html/2510.04173v4)). AGENTS.md is project instructions, used by 60,000+ projects ([LF](https://linuxfoundation.org/press/linux-foundation-announces-the-formation-of-the-agentic-ai-foundation)). Claude's memory import is a copy-paste prompt flow ([Claude Help Center](https://support.claude.com/en/articles/12123587-importing-and-exporting-your-memory-from-chatgpt-and-other-ai-providers)).

| Agent layer | Best existing standard | What is missing |
|---|---|---|
| Identity | A2A Signed Agent Card; MCP OAuth client | Portable keys and credential handoff |
| Charter | Open Agent Spec; AGENTS.md | A single versioned form tied to memory and evals |
| Memory | Letta .af memory blocks | Cross-vendor format |
| Files | MCP resources | Any export format with history |
| Permissions and approvals | OAuth scopes; EMA extension | Portable policy |
| History and audit | .af messages; A2A task history | Audit-log standard |
| Pending work | MCP Tasks; A2A tasks | Handoff between hosts |

No standard covers every row. An open **agent bundle** would: a signed manifest of content-addressed blobs holding the Agent Card, the charter (referencing Open Agent Spec or AGENTS.md), memory in .af-compatible shapes, files with full version history, permission and approval policy, the hash-chained audit and decision records, and pending tasks as A2A/MCP task objects, with secrets nulled following the .af precedent. Agent Cloud's content-addressed, versioned store is close to that bundle's natural on-disk form. Serving A2A endpoints per hosted agent, with artifacts persisted in the versioned store and push notifications sent over the existing signed webhooks, would make Agent Cloud the storage layer that both AAIF protocols currently leave undefined. Proposing the bundle as an MCP or A2A extension is speculative. Nobody checked whether an AAIF working group already covers agent state.

## A build order that compounds

The roadmap below is ordered by four tests: whether something is broken today, whether a later item depends on it, whether a competitor already ships it, and whether nobody does. Two competitors frame it. Fast.io sells hosted MCP storage with leases. Turso AgentFS is the open-source copy-on-write rival with a full operation audit. Agent Cloud wins by being the self-hosted product that does what neither does: provenance that crosses agents, branches with review, and erasure that regulators can verify.

| Priority | Build | Why now | Depends on |
|---|---|---|---|
| P0 | **MCP 2026-07-28 migration**: identity from `_meta` + token; briefing as tool/resource with a server-side cursor; Streamable HTTP and `Mcp-Method`/`Mcp-Name`; RFC 9728 PRM and RFC 8707 audience checks; `ttlMs` on immutable versions | Current handshake is retired; 2026-07-28 clients will not receive identity or briefing | — |
| P0 | **Per-version provenance record**: writer, task id, inbound `traceparent`, model, charter hash, input file@version read set, source class, signed | One record feeds taint, decision provenance, risk scoring, erasure lineage and staleness; cheap now, costly to backfill | P0 MCP (`_meta` trace context) |
| P0 | **`memory_20250818` backend** over workspace paths | Near 1:1 command mapping; cheapest adoption wedge for every Claude user | — |
| P1 | **Leases with fencing tokens** on file id or path prefix, exposed as MCP tools | Matches Fast.io/LucidLink; research shows claim tools carry most coordination value | — |
| P1 | **Task branches + atomic multi-file commit + rename-safe three-way merge**, reviewed through existing proposals | The standard agent-safety pattern (lakeFS, Dolt, Artifacts) that no self-hosted file workspace ships | Leases (optional) |
| P1 | **Taint propagation and labelled reads**, with endorse action and lineage/quarantine query | The clearest unoccupied gap; ASI06 makes it a buyer checklist item | Provenance record |
| P1 | **Sub-credential minting** (RFC 8693 shape, budgets, `task_id`, `not_after`), delegation tree, subtree revoke, measured kill switch | Re-share-subset already gives attenuation semantics; no self-hosted alternative | — |
| P1 | **Per-task resource budgets and runaway detectors** (bytes, files, proposals, egress, approvals; rewrite loops), 429 `budget_exceeded` | LLM gateways cannot see storage behaviour | Sub-credentials, task id |
| P2 | **Risk-scored proposals** (auto/review/block), batching, denial circuit breakers, fatigue telemetry, MRTR `input_required` | Turns `all` mode from rubber stamp into triage | Taint, provenance |
| P2 | **SQLite task table**: data-triggered wake-ups, waitpoint tokens, per-agent singleton, MCP Tasks extension | Data-triggered wake-ups are unclaimed by Temporal/DBOS/Inngest/Cloudflare | Provenance, P0 MCP |
| P2 | **Crypto-shredding + erasure ledger replayed on restore + receipts + retention policy object + legal hold** | EDPB expects demonstrable, restore-proof erasure; key hierarchy must exist before data volume grows | Key hierarchy audit |
| P2 | **Owner-of-record decay**: required sponsor, re-auth cadence, inactivity pause cascading to descendants, unused-grant report | Entra's model, self-hostable and chain-aware | Delegation tree |
| P3 | **OTel export** of Agent Cloud's own MCP spans; hash-chained monthly audit/decision partitions; ≥6-month default retention | AI Act floor exceeds hosted tracing defaults | Provenance |
| P3 | **Write-time derived views** (summaries, digests), versioned compaction summaries, embedding keys per model | Extends the measured 4x latency / 8x token win | — |
| P3 | **Staleness loop**: `capture(url)`, facts sidecar, re-verification job, contradictions in the briefing | No product closes it; reuses briefing and worker | Task table |
| P3 | **Agent profile + migration eval report**; **agent bundle export/import** (.af-compatible); **A2A host** per agent | Portability is the long-term moat; standards still forming | Most of the above |
| Later | Postgres metadata backend and S3 blob backend | SQLite single-writer caps task-claim throughput; S3 enables real cold tiers and lifecycle | — |

The roadmap relies on several open questions that need checking. Is the AES-GCM key hierarchy shredding-ready, and are encryption chunks also dedup units? Does `resources/subscribe` survive stateless MCP? Is crypto-shredding legally sufficient? That needs counsel, since neither the EDPB nor the ICO has ruled on it. Do the unverified per-workspace quotas and rate limits exist? None of the researchers inspected Agent Cloud's code. No demand evidence was gathered on self-hosted versus SaaS buyers, so the ordering reflects technical leverage, not validated willingness to pay.

## Conclusion

The survey changes what kind of product Agent Cloud should think of itself as. It does not need to compete with Temporal on durability, with Entra on identity, with LiteLLM on spend, or with Zep on memory. Each of those systems is strong inside its own store and blind at the handoff where one agent's output becomes another's input, months later, under a different model and possibly a different owner. A single signed provenance record attached to every file version and every credential edge turns out to be the common substrate for five of the nine problems: injection containment, decision provenance, risk-scored approval, verifiable erasure and staleness tracking. That makes it the highest-leverage thing to build after the forced MCP migration.

The second implication concerns timing. Standards are converging at the wire level: MCP and A2A are both under AAIF, MCP has gone stateless, and A2A is at v1.0. Both explicitly leave storage, retention and ownership undefined. A self-hosted, open-source workspace that implements both protocols and also defines how an agent's state persists and moves is filling a slot the standards bodies left empty on purpose. That slot will not stay empty for long. Cloudflare Artifacts, Dolt's rebrand and LucidLink's MCP launch all landed in 2026.
